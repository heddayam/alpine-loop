# Hike Builder implementation plan

## 1. Product outcome

Build a strong, region-independent foundation that generates plausible hiking
routes from a bounded trail graph. The first usable slice covers the Santa Cruz
Mountains, but regions are installed as data packs rather than encoded in UI or
solver logic.

The primary interaction is:

1. Draw or resize a rectangle on the map. The rectangle is a hard boundary for
   every returned route geometry.
2. Optionally select a known access point inside it. If none is selected, the
   solver may choose a suitable known access point.
3. Choose one or more route shapes, physical constraint ranges, the unknown
   access policy, and a requested result count from 1 to 20 (default 10).
4. Generate alternatives. Show exact matches first. Show up to three near misses
   in a separate labeled section with every violated constraint disclosed.
5. Compare route cards with their map geometry, metrics, warnings, source
   confidence, and optional elevation profile.

This is not a search index of named hikes. Names may be synthesized from access
points and major trail names, but the graph and constraints define the route.

## 2. Scope

### First release

- Rectangle draw/edit/clear and optional trailhead selection.
- Loop, lollipop, out-and-back, and point-to-point generation.
- Min/max ranges for distance, total elevation gain, maximum altitude, and
  steepest sustained grade.
- Route count selector from 1 to 20.
- Known-access-only default with an explicit “include uncertain access” toggle.
- Exact and near-miss results with deterministic ordering and route diversity.
- Santa Cruz Mountains coverage pack generated by one documented bootstrap
  command.
- Standard local Next.js development and production builds.

### Explicitly deferred

- Travel-time isochrones and drive-time filtering. Preserve the code under
  `legacy/isochrones/source`, but do not import or expose it.
- Accounts, saved hikes, collaboration, turn-by-turn navigation, mobile-native
  clients, hosted deployment, and real-time closure guarantees.
- Additional regions until the first pack proves the pack contract.
- Shade, surface, dog rules, accessibility, permits, and live closures unless a
  pack declares reliable capability fields for them.

## 3. UX and layout

Use a Caltopo-inspired information density without copying its visual design.

- Top bar: product name, installed pack/freshness, unit preference, help.
- Left builder panel: region status, rectangle instructions, start access point,
  route types, constraint ranges, unknown-access toggle, result count, Generate.
- Center: MapLibre map with USGS topo base, rectangle, access points, trail
  context, highlighted and alternate generated routes.
- Right results panel: exact matches, near misses, cards, sort, comparison, and
  route details. It is collapsed until results exist.
- Small screens: map remains primary; builder and results become mutually
  navigable drawers/bottom sheets.

Required states are empty, drawing, invalid rectangle, generating, partial
results, no exact results, data unavailable, request budget exhausted, and
cancelled. Keyboard operation, visible focus, non-color route distinctions, and
screen-reader status announcements are acceptance requirements.

## 4. Active stack and directory boundaries

- Next.js 16 App Router, React, TypeScript.
- MapLibre GL JS and its draw controls.
- Zod at request, manifest, adapter, and persisted-record boundaries.
- SQLite as the runtime pack format, with R-tree spatial indexes.
- Vitest or Node test runner for unit/integration tests and Playwright for the
  local browser path.
- Ordinary scripts: `npm run dev`, `npm run build`, `npm start`, `npm test`,
  `npm run lint`, `npm run typecheck`, and `npm run pack:bootstrap`.

Expected ownership boundaries:

```text
app/                    Next.js routes and page composition
components/builder/     builder inputs and validation
components/map/         MapLibre map, draw, access/route layers
components/results/     exact/near-miss comparison UI
lib/contracts/          shared Zod schemas and public types
lib/graph/              pack repository and graph primitives
lib/solver/             shape builders, search, scoring, diversity
lib/data/               adapters and pack compiler
scripts/                explicit source refresh and pack commands
data/fixtures/          tiny committed deterministic graph/source fixtures
public/                 static application assets only
legacy/                 build-excluded historical reference
```

Root `tsconfig` and lint/test discovery must exclude `legacy/**`. There must be
no root `.openai/hosting.json`, Vite/vinext config, Cloudflare worker config, D1,
R2, or deployment scripts.

## 5. Public route-generation contract

Implement `POST /api/routes/generate` with this versioned request shape:

```ts
type GenerateRoutesRequestV1 = {
  version: 1;
  packId: string;
  bbox: [west: number, south: number, east: number, north: number];
  startAccessPointId?: string;
  routeTypes: Array<"loop" | "lollipop" | "out-and-back" | "point-to-point">;
  distanceMiles: { min: number; max: number };
  elevationGainFeet?: { min: number; max: number };
  maximumElevationFeet?: { min: number; max: number };
  steepestSustainedGradePct?: { min: number; max: number };
  includeUncertainAccess: boolean;
  limit: number; // integer 1..20, defaulted by client to 10
};
```

Validate finite coordinates, ordered ranges, supported pack, rectangle inside
pack coverage, maximum rectangle area, at least one route type, and explicit
request limits. Store and calculate internally in SI units; translate only at
the API/UI boundary.

The response must contain:

```ts
type GenerateRoutesResponseV1 = {
  version: 1;
  requestId: string;
  pack: { id: string; schemaVersion: string; dataVersion: string; builtAt: string };
  requested: number;
  exact: GeneratedRoute[];
  nearMisses: Array<GeneratedRoute & { violations: ConstraintViolation[] }>;
  diagnostics: {
    elapsedMs: number;
    expandedStates: number;
    candidateCount: number;
    exhausted: boolean;
    truncationReasons: string[];
  };
};
```

Each route includes a deterministic ID, shape, GeoJSON LineString, start/end
access points, distance, elevation gain/loss, minimum/maximum altitude, steepest
sustained grade, repeated-edge fraction, trail-name summary, warnings, source
freshness/confidence, and optional elevation samples. Returning fewer than the
requested count is valid and must be explained. Never pad with duplicates.

## 6. Metric and route definitions

- **Distance:** sum of traversed edge geometry lengths, not straight-line node
  distance.
- **Elevation gain/loss:** sum direction-aware, noise-filtered elevation changes
  along densified geometry. The pack compiler owns one algorithm for all edges.
- **Maximum altitude:** maximum sampled route elevation.
- **Steepest sustained grade:** largest absolute rise/run over any rolling 100 m
  route window. It is not the steepest single DEM sample.
- **Loop:** begins and ends at the same known access point and has no repeated
  undirected edge except negligible access connectors.
- **Lollipop:** a shared out-and-back stem joined to a simple cycle; repeated
  non-cycle distance may not exceed 35% of the total.
- **Out-and-back:** an outward path followed over the same edges in reverse.
- **Point-to-point:** distinct known access points; always show a shuttle/two-car
  warning.

Respect directed edge legality. Forward and reverse traversal can have different
access status, gain, and loss. Reject private, closed, prohibited, or
non-pedestrian edges. Exclude `unknown` access unless the request explicitly
enables it.

## 7. Solver design and tractability budgets

Keep a `GraphRepository` interface between the solver and SQLite so fixture
graphs and future pack formats do not change solver code.

1. Query spatial indexes for nodes, edges, and access points intersecting the
   rectangle; clip by geometry and reject any candidate that leaves the hard
   boundary.
2. Resolve the requested access point or rank eligible starts by known public
   access confidence, parking/trailhead evidence, and graph connectivity.
3. Build candidates with shape-specific algorithms:
   - out-and-back: bounded path labels from the start near half the target range;
   - loop: bounded cycle search around the start;
   - lollipop: bounded stem labels plus compatible cycles;
   - point-to-point: bounded labels to distinct eligible access points.
4. Use multi-criteria beam search / nondominated labels bucketed by distance and
   gain. Apply feasibility bounds early and score complete candidates later.
5. Deduplicate canonical edge sequences, then greedily select diverse results.

Hard defaults, configurable in one server-side budget object:

- maximum 10,000 directed edges in the induced graph;
- maximum 100,000 expanded search states;
- 3,000 ms server deadline;
- maximum 2,000 raw candidates before final scoring;
- cancellation/abort checks inside expansion loops.

If a limit is reached, return partial deterministic results with a diagnostic;
do not hang or silently broaden the search.

Exact results satisfy every requested range. Score them by closeness to range
centers, known access quality, low repetition, trail-name continuity, and source
confidence. Diversity selection should reject a candidate when more than 80% of
its undirected distance overlaps an already selected route. Tie-breaking must be
stable by canonical route ID.

Near misses are the best candidates violating the fewest constraints by the
smallest normalized amount. Return at most three in their own array, with values,
bounds, and deltas for every violation.

## 8. Region-pack contract

The UI discovers installed packs from manifests; it never contains special
branches for “Midpen” or “Santa Cruz.” A pack includes:

- a SQLite graph database;
- a JSON manifest validated by a versioned schema;
- pack boundary and display metadata;
- source snapshot identifiers, URLs, retrieval times, hashes, and licenses;
- capabilities and field-level confidence/freshness;
- compiler version and metric algorithm version.

Minimum runtime tables:

- `nodes(id, lon, lat, elevation_m, flags)` plus spatial index;
- `edges(id, from_node, to_node, geometry, length_m, gain_m, loss_m,
  max_elevation_m, max_sustained_grade_pct, access_state, source_refs, flags)`
  plus spatial index;
- `access_points(id, node_id, name, kind, access_state, confidence,
  parking_evidence, source_refs)`;
- `sources(id, authority, dataset, version, retrieved_at, url, license,
  content_hash)`;
- metadata and schema migration records.

Use compact encoded geometry and create both legal directed edges when travel is
bidirectional. Keep raw downloads and built databases under ignored directories.
Commit only tiny licensing-safe fixtures and manifests needed by tests.

The first `npm run pack:bootstrap -- --pack=santa-cruz-mountains` command must:

1. validate required local tools and disk space;
2. download or reuse pinned raw source snapshots;
3. spatially extract the coverage boundary;
4. normalize topology/access and attach official overlays;
5. sample elevation and compute edge metrics;
6. validate connectivity, geometry, metrics, attribution, and manifest;
7. publish atomically into `.local-data/packs/<pack-id>/<data-version>/`.

Failed builds must not replace the last valid local pack.

## 9. Error and safety behavior

- Reject overlarge/degenerate/out-of-coverage rectangles with an actionable
  message before searching.
- A route is a planning aid, not an assurance that a trail is open or safe.
  Display data dates and a “verify current conditions” warning.
- Show explicit warnings for uncertain access, point-to-point logistics,
  incomplete elevation, stale official data, and search truncation.
- No runtime call to the public OSM API or Overpass.
- Never log secrets or raw user location history. The first release needs no
  persistent user-location store.

## 10. Acceptance gates

### Gate 0 — foundation

- Standard Next.js app installs and passes lint, typecheck, tests, and build.
- Shared request/response/manifest schemas exist and have boundary tests.
- A tiny synthetic SQLite/fixture graph supports all route shapes.
- Legacy and generated data are excluded from build and Git.

### Gate 1 — independent foundations

- Map shell supports drawing/editing/clearing one rectangle and selecting a
  fixture access point.
- Pack compiler can turn committed source fixtures into a validated fixture pack.
- Solver enforces graph direction, hard boundary, access policy, budgets, and
  deterministic IDs on fixture graphs.

### Gate 2 — vertical slice

- UI calls the real local API and renders generated geometry/cards.
- All four route shapes, min/max metrics, 1–20 count, diversity, exact/near-miss
  separation, cancellation, and diagnostics have deterministic tests.
- Browser test completes the draw → configure → generate → inspect path.

### Gate 3 — first real pack

- One command builds the Santa Cruz Mountains pack from pinned sources.
- Audit reports topology connectivity, rejected edges, access-state counts,
  missing elevation, implausible metrics, and source attribution.
- A curated set of rectangle/request scenarios produces useful routes within the
  budgets on a typical development laptop.

### Gate 4 — hardening

- Responsive and keyboard UX passes accessibility checks.
- Empty/error/partial/stale/cancelled states are clear.
- Fresh clone instructions work with only documented prerequisites.
- No obsolete worktree, deployment configuration, or generated data is tracked.
